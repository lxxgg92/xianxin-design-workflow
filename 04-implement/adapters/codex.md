# implement

按照 Handoff.md 实现页面代码。在 handoff 完成且用户确认后触发。

## 前置判断
- 执行前检查以下文件和资源是否存在，缺少任意一项时，**一次性列出所有缺失项**后统一反馈，不逐条追问：
  - Handoff.md
  - UI_SPEC.md 或 UI_SPEC_*.md
  - DESIGN.md
  - 目标页面文件（根据 Handoff.md 中的修改范围定位）
  - 相关组件文件（根据 Handoff.md 中的修改范围定位）
- 如果目标页面或相关组件找不到，告知用户具体缺失的文件路径，等用户确认再继续

## 输入
- Handoff.md
- UI_SPEC.md 或与当前页面对应的 UI_SPEC_*.md（多页面项目）
- DESIGN.md
- 现有页面代码与组件（如有）

## 输出
- 页面代码文件
- 标准交接信息：
  - 改动文件列表
  - 新增组件列表
  - 验证状态（本地构建或开发服务器启动后页面无报错、可正常访问）
  - 冲突说明

## 职责
在开始编码前必须完成以下准备工作：
1. 阅读整个项目结构
2. 找到目标页面位置
3. 查找现有组件和样式写法
4. 阅读 DESIGN.md 设计系统规则，识别 YAML 中定义的 token（颜色、字号、间距、圆角、组件），在代码中使用对应的 CSS 变量或样式值，不允许硬编码脱离 token 体系的数值
5. 运行 DESIGN.md lint 验证，确认 token 引用无 broken reference、WCAG 对比度合格：
   ```bash
   npx @google/design.md lint DESIGN.md
   ```
   - 如有 **error** 级别报错（如 broken token reference）：必须先修复 DESIGN.md 再继续
   - 如有 **warning** 级别报错（如 WCAG 对比度不足）：可继续，但记录在冲突说明里
6. 阅读 UI_SPEC.md
   特别关注'状态规则'章节中的性能约束（虚拟滚动、懒加载、大数据量增量加载等），确认实现中已覆盖
7. 阅读 Handoff.md
8. 判断最小改动范围，确定改动边界

准备工作完成后，**必须先暂停**，向用户说明：
- 计划修改哪些文件
- 计划新增哪些组件（如有）
- 改动边界（哪些文件不会被动）
- 等用户确认后再开始写代码

页面实现时需要遵守：
- 优先复用已有组件
- 优先复用已有样式变量
- 保持项目原有代码风格
- 尽量只修改与本页面相关的文件
- 不要随意创建新文件
- 不要随意安装新依赖
- 不要修改无关业务逻辑
- 不要删除已有功能
- 不要把临时调试代码留在项目中
- 不要硬编码颜色、字号、间距等设计值，必须使用 DESIGN.md token 或导出的 CSS 变量

如需新增组件：
- 说明为什么不能复用旧组件
- 说明新组件放置位置
- 说明该组件后续是否可复用

输出执行信息作为标准交接信息，供 verify 和 deliver 优先读取；跨轮次或上下文缺失时，再向用户确认。

## 冲突处理
如果发现现有代码与设计要求冲突：
1. 先记录冲突内容到 Handoff.md
2. 向用户说明冲突点和建议方案
3. 必须暂停，等用户确认后再执行最小范围调整

## 暂停点
- **准备工作完成后**：告知计划改动范围，等用户确认再开始写代码
- **发现代码与设计冲突时**：说明冲突点和建议方案后暂停，等用户确认再继续

## 上下游关系
- 依赖：Handoff.md、UI_SPEC.md、DESIGN.md
- 输出：页面代码，供 verify 验收
- 下游：下一步进入 → verify
