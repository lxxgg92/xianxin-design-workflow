# verify

通过截图对比验收页面实现质量。在 implement 完成后，由用户确认进入，或用户手动触发。触发前确认页面已能正常访问，不应在页面构建失败时执行截图对比。

**自动化选项**：如果需要并行检查 8 个验收维度（布局、字体、颜色、组件、状态、交互、响应式、性能），可以使用 Workflow 自动化版本，运行方式：
```
使用 workflow 运行 screenshot-verify
```
自动化版本会用 7 个 agent 并行检查，最后汇总成一份偏差报告，比手动逐项检查更快。

## 前置判断
- 如果用户没有提供参考图 / 原型 / Figma 截图，必须先向用户索要，不能只凭 DESIGN.md 和 UI_SPEC.md 进行对比
- 如果确实没有参考图，需明确告知用户：对比结果仅基于设计规范，无法判断视觉还原度
- 收到参考图后，先向用户确认：**这张参考图对应的是当前要验收的页面吗？**（防止用户传错参考图或混用其他页面的截图）

## 输入
- 当前页面截图
- 参考图 / 原型 / Figma 截图
- DESIGN.md
- UI_SPEC.md 或与当前页面对应的 UI_SPEC_*.md（多页面项目）
- Handoff.md
- implement 的标准交接输出（改动文件、验证状态、冲突说明）
- 项目现有页面风格（从现有页面代码中读取）

## 输出
- 偏差报告，包含：
  - 符合的地方
  - 不符合的地方
  - 偏差等级（严重 / 中等 / 轻微）
  - 修正建议
  - 是否需要继续修改代码

## 职责
对比页面和设计标准，重点检查以下 7 个维度：

1. **布局**：模块顺序、对齐、间距、页面重心、是否拥挤或过空
2. **字体**：字号、字重、行高、标题/正文/辅助文字层级
3. **颜色**：主色是否与 DESIGN.md YAML 中 `colors` token 一致、背景色、边框色、状态色、是否出现未定义的颜色值
   - **额外检查**：用 grep 确认代码中是否有硬编码颜色（可选，时间允许时执行）：
     ```bash
     grep -rn "#[0-9A-Fa-f]\{3,6\}\|rgb\|rgba" src/
     ```
     如发现硬编码，记录在偏差报告的"不符合"项中
4. **组件**：组件样式是否与 DESIGN.md `components` token 中定义的属性一致（颜色、圆角、字号、内边距）
5. **状态**：默认态、空状态、加载态、错误态、无权限态、disabled 是否清晰
6. **交互**：点击反馈、hover 自然度、表单校验、弹窗关闭、删除确认
7. **响应式**：大屏显示、小屏不溢出、表格小屏可用、按钮换行、内容不遮挡
8. **性能**：检查性能约束是否满足 UI_SPEC.md 中定义的要求
   - 列表数据量检查：超过 100 条是否使用了虚拟滚动或分页加载
   - 图片资源：是否配置了懒加载、占位图、加载失败降级方案
   - 大数据集渲染：是否有增量加载或骨架屏提升感知性能
   - 加载超时：是否有超时处理和重试机制

必须指出具体检查结果，不可只说"看起来没问题"。

输出信息供后续 deliver 优先结合 implement 的标准交接信息进行判断；跨轮次或上下文缺失时，再向用户确认。

## 流转逻辑
对比完成后，根据偏差等级决定下一步：
- **严重偏差**：告知用户具体问题，建议回到 implement 修改，等用户确认后再执行，不自动触发
- **中等偏差**：告知用户，由用户决定是否继续修改
- **轻微偏差**：记录在报告中，可进入 deliver

迭代轮次由用户或全局系统告知；如未告知，在本轮报告中注明"当前为第 N 轮截图验收/修正"并请用户确认。

迭代上限：如果已经迭代超过 3 轮仍有严重偏差，必须暂停并升级给用户决策，说明具体卡点，不再自动建议继续修改。

## 暂停点
- 收到参考图后：先确认参考图是否与当前验收页面对应，等用户确认后再开始对比
- 偏差报告生成后：必须暂停，向用户说明报告结果，等待用户确认后再决定下一步
- 严重偏差时：告知用户具体问题，建议回到 implement 修改，不自动触发
- 迭代超过 3 轮仍有严重偏差：必须暂停并升级给用户决策，说明具体卡点

## 上下游关系
- 依赖：implement 的输出（页面代码）、参考图、DESIGN.md
- 输出：偏差报告，供 deliver 使用
- 严重偏差时回退到 implement
- 下一步进入 → deliver
