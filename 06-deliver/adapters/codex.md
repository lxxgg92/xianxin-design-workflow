# deliver

判断页面是否可交付并生成最终交付报告。在 verify 偏差报告显示"轻微偏差"时，由用户确认后进入；或由用户手动触发。不应在 verify 仍有严重偏差或中等偏差未处理时触发。

## 前置判断
- 执行前检查以下文件是否存在，缺少任意一项时，**一次性列出所有缺失项**后统一反馈，等用户补充或确认后再继续：
  - DESIGN.md
  - UI_SPEC.md 或与当前页面对应的 UI_SPEC_*.md（多页面项目）
  - Handoff.md
  - verify 的偏差报告（如果没有，说明截图验收尚未完成，建议先运行 verify）
- 条件第 4、5 条（页面正常运行 / 无控制台报错）优先依据 implement 的输出中的验证状态判断：
  - 如果在同一对话中，直接从上下文获取
  - 如果不在同一对话（跨轮次），需向用户确认：**当前页面构建是否成功、是否有控制台报错？**

## 输入
- 页面实现
- verify 输出的偏差报告
- implement 的输出（改动文件、验证状态、冲突说明）
- DESIGN.md
- UI_SPEC.md 或与当前页面对应的 UI_SPEC_*.md（多页面项目）
- Handoff.md
- 当前项目页面代码

## 输出
- 可交付状态（是/否）
- 说明与建议
- 将输出结果写入项目根目录的 delivery-report.md，包含：
  - 是否可交付
  - 本次完成了什么
  - 主要改动文件
  - 已验证内容
  - 剩余风险
  - 后续建议

## 职责
判断页面是否可交付，检查以下 9 个条件：

1. 页面符合 DESIGN.md 的项目级设计系统
2. 页面符合当前页面对应的 UI_SPEC.md 或 UI_SPEC_*.md 的结构和交互要求
3. 已完成 Handoff.md 中的实现任务
4. 页面能正常运行（优先依据 implement 标准交接输出中的验证状态判断，无需自己重新运行页面；跨轮次时向用户确认）
5. 控制台没有明显报错（同上）
6. 页面主要状态已在前序阶段完成验证（默认态、加载态、空状态、错误态、无权限态）
7. 响应式已在前序阶段验证基本可用
8. 依据 verify 的偏差报告判断主要视觉差异已收敛
9. 没有破坏其他页面

提供最终交付建议，便于用户决策后续方向。

## 不可交付时的处理
如果判断为不可交付，必须明确说明：
- 哪些条件未满足
- 建议回退到哪个步骤处理（implement 或 verify）
- 预计需要修改的范围

   **回退路径映射**：
   - 条件 1-2 未满足（不符合 DESIGN.md 或 UI_SPEC.md）→ 回退到 spec 或 design 重新确认规格
   - 条件 3 未满足（Handoff.md 任务未完成）→ 回退到 implement 继续实现
   - 条件 4-5 未满足（页面构建失败/控制台报错）→ 回退到 implement 修复错误
   - 条件 6-8 未满足（状态缺失/响应式异常/视觉差异）→ 回退到 implement 或 verify 确认差异
   - 条件 9 未满足（破坏其他页面）→ 回退到 implement 修复冲突

## 暂停点
- 判断为可交付时：输出 delivery-report.md 后告知用户，等待用户确认
- 判断为不可交付时：说明未满足的条件和建议回退路径后暂停，等用户决定是回退修改还是强制交付

## 上下游关系
- 依赖：verify 的偏差报告、DESIGN.md、UI_SPEC.md、Handoff.md、implement 的输出
- 输出：可交付状态报告（最终节点）
- 如不可交付：回退到 implement 或 verify
- 下一步进入 → spec（如需开始新页面）
